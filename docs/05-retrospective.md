# 最难问题、学习收获、下一步

## 最难的问题

这轮我没有继续扩展功能，主要补现有执行链路里的缺口：模型可以选动作，但程序必须用当前证据决定动作能否执行。

### 观察在模型调用期间失效

上下文组装时有效的资料，到工具真正执行时可能已经变化。
如果展示和工具保护各自维护一套判断，也容易出现一边提示失效、另一边仍然放行的情况。

我把有效性判断合并，并放到每次工具执行前复查。业务保护继续使用完整观察，摘要和投影不代替证据。
这样处理后，模型即使沿用旧结论，也需要先重新获取有效资料才能继续。

### 最早时段和有效确认有不同的优先级

新排期要选择最早空位，但用户已经确认的时间不能被随意替换。
例如用户确认19点后，18点重新空出，程序仍应保存有效的19点确认，不能自动改回18点。

我把这两种情况放进保存事务里区分，同时核对查询快照和最新占用。
占用变化时返回重查；成功写入的请求继续复用原草稿，避免加固过程破坏幂等。

### finish也需要证据

模型说“资料不足”“审核阻断”或“没有时段”，都应对应当前工具结果。
我补齐这些结束条件，并保留incomplete作为主动退出，避免把工作未完成误写成业务阻断。
业务错误返回给模型纠正，运行故障和预算耗尽另外记录。

本轮演示里，模型第一次错选20点，程序拒绝后它改用实际查询中的17点，最终只保存一份草稿。
这个过程验证了程序能拦住错误，也保留了模型根据观察继续调整的空间。

### 日志故障不能覆盖保存成功

草稿保存成功和Trace写入成功是两件事。日志失败如果被当成工具失败处理，会让数据库事实与请求状态矛盾。
我隔离了预期的日志写入故障，向标准错误告警，保持JSON标准输出可解析。
记忆和Trace同时故障时也能降级，不在处理日志错误时再次写同一故障日志。

这里仍有取舍：业务能继续，但审计可能不完整。告警不会变成新的数据库字段，之后查询不能还原已经丢失的日志。

## 我的学习收获

1. 提示词里的要求需要有对应的程序校验。最早候选、确认时间和结束原因，都应能用测试与数据库事实检查。
2. 证据不仅有内容，还有来源和有效期。模型调用前检查一次不够，执行前和保存事务内各有需要检查的条件。
3. 模型主动退出、业务拒绝、运行故障和预算耗尽不能混成一个状态，否则结果难以解释，也容易误判成功。
4. 数据消息不应该进入system角色。消息角色和工具保护都要处理，但离线注入测试通过不能证明完全免疫提示注入。
5. 小范围加固也要检查恢复、幂等和故障路径。新增保护不能让已写入草稿在重放时重复保存，也不能让日志故障改写业务结果。
6. 测试和真实模型验证回答的问题不同。95项离线通过说明受控场景下程序行为符合预期，真实模型是否理解新增约束仍需另测。

前期上下文测试也给了我一个提醒：长输入的token可以下降，短流程却可能增加成本。
本轮没有重新做真实API或成本对比，我保留原记录，不把以前的收益写成这次的验证结果。

## 本轮验证和限制

修改前基线64项通过、1项跳过；首批新增测试在修复前出现7个预期失败。
修复后定向69项通过，全量95项通过、1项跳过，独立wheel环境结果相同。
Ruff、格式、Mypy、语法和打包通过，目录外CLI运行、查询及数据库事实也已核验。

首次离线安装因缓存解析受限失败，之后按已锁定版本安装并检查兼容性。
这段失败保留在[评估文档](03-evaluation.md)，没有只留下最后的成功输出。

本轮未调用真实API，没有覆盖历史记录。JSON与SQLite仍没有跨介质事务，Trace故障仍可能造成审计缺失。
项目支持单机CLI、合成元数据和同日整点排期，只保存草稿；不包含真实发布、视频理解、跨日搜索或在线部署。
